# External-data feasibility investigation: remaining pre-ML blockers

**Investigation type:** read-only external-source review, performed 2026-09-11. No external data was downloaded, no project data/code was changed, and no labels, negative samples, spatial links, models, predictions, or scores were created.

## Executive finding

**Recommendation: C. ML remains scientifically blocked.**

Authoritative sources identify plausible routes to obtain better boundary and event documentation, but the public evidence reviewed does not itself satisfy all three blockers. In particular, no reviewed source establishes a Nilgiris-village, unit-period observation frame under which a missing landslide record can be treated as `no_event = 0`. That evidence is required before a supervised binary target can be constructed.

The SoI Online Maps Portal describes the Village Boundary Database as state, district, taluk/sub-district, and village administrative boundaries; the portal FAQ/product catalogue describes Shapefile and Geodatabase delivery. | **Most promising authoritative acquisition route.** It establishes that an official village-polygon product exists, but this review did not download it. ### Boundary conclusion

One source *may* provide the desired complete layer: the SoI Tamil Nadu Village Boundary Database is the leading candidate because SoI officially advertises village-level vector boundaries and a Tamil Nadu release. However, no download or inspection was authorized in this phase, so completeness, LGD-code compatibility, district/taluk attributes, CRS, vintage, and licence remain unverified. It would be scientifically premature to assert that any one currently inspected public service already provides the complete, internally consistent Nilgiris layer.

**Minimum verification before accepting a boundary source:** obtain the authoritative vector release and accompanying metadata; inspect its CRS, source/version/vintage, licence, field dictionary, and all Nilgiris records; verify unique village IDs and exact district/taluk/village LGD compatibility against a versioned LGD extract; and reconcile every expected/observed unit without names, proximity, or geometry inference.

| GSI/NLFC, **Nilgiris 2025 incidence report** | [GSI incidence report](https://bhusanket.gsi.gov.in/Output/LS_Incidence_Report/2025/Landslide%20incidences%20in%20the%20Coonoor,%20Kundah%20and%20Kotagiri%20taluks%20of%20the%20Nilgiris%20District,%20Tamil%20Nadu,%2009.11.25%20to%2016.11.25..pdf) | A date-bounded report containing 42-point geo-parametric records, including separate latitude, longitude, and date-of-reporting fields. | Shows that official field reports can expose coordinate values and distinguish date of reporting. It does **not** provide a formal coordinate reference system/datum declaration, positional accuracy, or metadata for the older supplied PDF. It is useful supporting evidence for requesting a field dictionary, not a substitute for it. |
| GSI/NLFC, **FAQ and project metadata pages** | [FAQ](https://bhusanket.gsi.gov.in/faq.html), [project metadata](https://bhusanket.gsi.gov.in/projectMetadata.html) | The FAQ describes inventory as a georeferenced spatial database with spatial and temporal attributes; project metadata requests latitude/longitude and study-period information. | Describes programme concepts, but no reviewed text specifies the datum/EPSG, latitude/longitude storage convention, precision, or historical inventory version metadata for the supplied file. |

### CRS/datum conclusion

**Authoritative documentation for the supplied “Landslide Inventory (Field Validated)” PDF’s coordinate CRS/datum was not found in the reviewed official public materials.** The materials support only that GSI/NLFC uses latitude/longitude fields and that some reports display north/east or decimal-degree values. That is not evidence of a particular datum, CRS, coordinate accuracy, or field meaning for the supplied PDF. CRS must not be inferred from coordinate ranges, display format, KML compatibility, or a web-map default.

Before any overlay, request from GSI/NLFC the inventory release/version date; authoritative data dictionary; coordinate CRS/EPSG and datum; axis convention; coordinate capture method and expected precision/accuracy; definitions of latitude/longitude fields; definitions of `History`, occurrence date, date range, and reporting date; coverage/completeness statement; and confirmation that these metadata apply to the supplied source file.

## 3. Blocker: observation / monitoring completeness

### Sources reviewed

| Organization / source | Official URL | What it provides | Can it establish village-period non-events? |

| Tamil Nadu TiNAI Geospatial Platform | [TiNAI](https://tnslurb.tn.gov.in/tinai/) | Viewer for historical Western Ghats landslide inventory and susceptibility layers. | **No evidence found.** The reviewed public description supplies visualization context but no inventory observation protocol, geographic denominator, reporting-period completeness, or negative-event assertion. |

### Observation-frame conclusion

The official sources demonstrate useful activity: incident reporting, field inventory collection, some site monitoring, preparedness, and alert dissemination. None of the reviewed materials documents an all-Nilgiris-village, time-indexed observation frame with coverage dates, detection/reporting rules, and a statement that no record during coverage means no observed landslide. Therefore they cannot support `no_event = 0` labels.

The required evidence is not simply another event inventory. It is a provider-issued observation protocol/dataset containing, at minimum: covered spatial units or coverage geometry; start/end dates (and gaps); observation method and cadence; reporting channels; event definition and detection threshold; inclusion/exclusion rules; whether zero-event reporting is explicit; and an auditable unit-period denominator. Without it, unrecorded periods remain unknown.

## Recommended data requests and decision gate

1. **SoI first:** request/access the Tamil Nadu Village Boundary Database plus metadata and licence; inspect it offline only after authorization, then compare its versioned identifiers to LGD without fuzzy matching.
2. **TNGIS/LGD parallel confirmation:** request a formal TNGIS polygon service/download specification and metadata; use versioned LGD only as the administrative reference, not geometry.
3. **GSI/NLFC metadata request:** obtain written confirmation applying specifically to the supplied inventory release: CRS/datum/EPSG, coordinate semantics and accuracy, date/history semantics, version/date, and coverage statement.
4. **Observation-frame request:** ask GSI/NLFC and Nilgiris DDMA whether a geographically complete, time-bounded landslide surveillance/reporting register with explicit zero-event coverage exists. If it does not, record that absence as a study-design constraint rather than generating negatives.

Only if all four requests yield compatible, documented real evidence should FloodGuard repeat the target-readiness audit. Even then, approval would require a pre-specified modelling unit, target time resolution, feature aggregation method, and spatial/temporal leakage-control plan. Until then, a separately scoped **evidence-based non-ML hazard assessment** could be considered, but it must not be represented as supervised prediction or use fabricated risk labels.
